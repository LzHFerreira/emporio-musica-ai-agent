# Interface contracts

Status: signed local ingress, worker, source maintenance and customer tools are implemented. Contracts below are full acceptance targets; [validation](validation.md) records evidence and gaps. Live Meta compatibility and generated-answer quality are unverified. PDF ingestion runs in-process with pypdfium2 and needs no system install.

## Shared backend and local transport

Django 5.2/SQLite serves staff pages and signed webhooks; a separate worker processes durable jobs. CSV/PDF sources remain canonical. `demo_chat` uses scripted responses; `interact_chat` exercises the configured model through the same webhook, worker, tools and mock Meta client. Neither is the full operator UI. Local egress uses the Meta `httpx` client; fixtures, not implementation output, define wire expectations.

## Customer CLI

`uv run --env-file .env python manage.py interact_chat --message TEXT` runs one turn; omit `--message` for stdin until `/quit` or EOF. `MODEL_PROVIDER` defaults to `cloudflare`; supported explicit values are `cloudflare`, `ollama`, `openai`, `anthropic`, and `openrouter`. `cloudflare` defaults to `@cf/zai-org/glm-4.7-flash`; `@cf/google/gemma-4-26b-a4b-it` remains on the reviewed free-eligible list and can be selected with `CLOUDFLARE_MODEL`. Live development-set results (the first five of the nine fixed questions, three runs each, not an independent quality measure) are in [validation](validation.md): GLM 13/15, Gemma 11/15. Cloudflare requires `CLOUDFLARE_ACCOUNT_ID` plus `CLOUDFLARE_API_KEY` or `CLOUDFLARE_API_TOKEN`, and supports an optional `CLOUDFLARE_MODEL` override. A model outside the reviewed free-eligible list requires `ALLOW_PAID_MODELS=true`; this acknowledges cost risk, not model quality or provider charges. `ollama` uses `OLLAMA_BASE_URL`, `OLLAMA_MODEL` and `OLLAMA_TIMEOUT_SECONDS` (default 180 s per request). Five live conversations recorded with local `qwen3.5:9b` are in [interactions](interactions.md). `openai` and `anthropic` require `ALLOW_PAID_MODELS=true` and their own provider key; the OpenAI default is `gpt-6-luna` with `OPENAI_API_MODE=responses`. `OPENAI_REASONING_EFFORT` is optional and unset by default; when unset, the Responses request omits reasoning configuration. OpenAI also supports `chat_completions`, which forces `reasoning_effort=none` for GPT-6 Luna compatibility. Anthropic defaults to `claude-haiku-5-5`. OpenRouter requires `MODEL_PROVIDER=openrouter`, `OPENROUTER_API_KEY` and `OPENROUTER_MODEL`; only `:free` routes can be selected without the paid-risk flag. Unknown providers, missing provider credentials and disabled paid selection fail explicitly. There is no cross-provider fallback or key sharing. Exact setup and current model costs are in the [README](../README.md#running-the-project) and [ADR-0004](adr/0004-free-model-and-provider-fallbacks.md). The command uses a synthetic sender unless `--sender` names one, and local services, not Meta credentials. Plain Python does not load `.env`. `demo_chat` is a separate scripted demo.

The provider adapter uses a Gemma-specific private function, `respond_to_customer`, for the final structured reply. It has no lookup or order access; the existing terminal parser and evidence checks still validate its output. The adapter adds it only to the direct Gemma request, not to the shared four-tool registry or the MCP server. For Gemma only, the adapter copies the `search_catalog` schema and requires a string `query`; an empty string remains the explicit general-browse request. A missing/non-string query is rejected before a business tool runs. The canonical registry and MCP schema are unchanged. Other Cloudflare models keep the existing tool protocol.

## MCP server

Run `uv run --env-file .env python manage.py mcp_server` to start the local stdio MCP server using the locked `mcp==1.30.0` SDK. It exposes exactly `search_catalog`, `lookup_public_policy`, `list_own_orders`, and `get_own_order_status`; schemas are recorded in [tool-schemas.json](tool-schemas.json). The tools call the same application services and authorization checks as the customer agent. MCP clients supply their own model and decide when to call tools; MCP tool service does not use `MODEL_PROVIDER` to run model inference.

`EMPORIO_MCP_SENDER` is optional trusted server-side context for the two owned-order tools. Without it, those calls return the same generic denial. Sender, customer, provider, model and source-version selection are not tool arguments. An MCP client does not authenticate a sender by claiming one in tool input; order access is limited to the trusted server configuration and existing owner checks. The MCP server uses local stdio; this contract does not establish authentication for a remotely exposed MCP endpoint.

Each tool call selects the currently active source bundle independently. Successful tool results include `bundle_version`; unlike a queued Django customer turn, the MCP server does not pin a bundle version across separate calls. An MCP host combining multiple results should compare their `bundle_version` values and avoid combining results from different publications.

Each MCP tool call independently reads the currently active source version, pins that call to it, and returns `bundle_version` in source provenance when available. A publication between calls can therefore make one external host's multi-call conversation span versions. Clients that need a consistent multi-call view must detect version changes in returned provenance and restart or reconcile the turn. The local Django chat loop instead pins one version for its turn and checks that version again before dispatch; this application behavior does not provide an MCP-wide turn guarantee.

The full harness acceptance includes transcript role/time/reply/delivery/takeover state; trusted fixture sender selection; submit/replay/failure/delay/restart controls; and operator takeover/reply/release. Customer text grants no harness privilege. Use display aliases only; sender numbers and matching details stay out of model context, transcript and ordinary logs. Accept text only; unsupported types get a fixed explanation without model execution. Product lookup uses descriptive references, never internal IDs.

## Webhook ingress

- GET subscription verification returns `hub.challenge` only for valid `hub.mode` and separate `hub.verify_token`.
- Verify POST `X-Hub-Signature-256` as HMAC-SHA256 over the exact raw body, then validate business/account/phone scope before trusting sender or envelope. Never log/store raw bodies.
- Validate, minimize and deduplicate before durable acceptance; acknowledge promptly without awaiting the model. Invalid events create no job/call. Status callbacks undergo the same checks, update delivery only and never start a turn.
- Parse all `entry[]/changes[]/messages[]/statuses[]`; sender scope comes from `metadata.phone_number_id`, status provider IDs from `statuses[].id`. Ignore unknown optional fields. Pin `META_API_VERSION=v24.0`; wire fixtures and provenance are in [fixtures](fixtures/meta-v24/README.md). Pin webhook subscription version separately for live setup.

## Message and delivery contracts

| Event | Required fields | Effect |
| --- | --- | --- |
| Incoming text | Provider message ID (dedupe key); business/account/phone scope; sender reference; occurred/received times; type/text; optional reply reference | Validate/minimize/dedupe, persist job, acknowledge. |
| Outgoing reply | Local reply/source IDs; server-derived recipient; author; creation time; validated text | Send through Meta client; persist provider ID and acceptance separately from delivery. |
| Delivery update | Provider ID; recipient/business scope; time; sent/delivered/read/failed; bounded error category | Update delivery only. |

Order accepted work by recorded receipt per business/channel/sender; timestamps do not establish identity. Resolve reply references inside that conversation. Deduplicate by business-phone scope and provider ID across restarts; conflicting sender/content reuse is rejected via protected fingerprint. Duplicates get no second model call/send; cached replies require current authorization/source checks. Record accepted/duplicate/rejected/interrupted. Never automatically rerun interrupted work.

Persist conversation, job, reply, source version, counters, takeover and delivery state. Keep queued distinct from sent/delivered/read/failed/unknown; status regressions cannot erase stronger delivery evidence. Retry at most one proven safe transient failure inside the original deadline; never retry an uncertain send. Delayed customer turns retain history without inactivity expiry; processing timeout fails one turn, not the conversation.

Handoff atomically changes `automation → human_pending`, invalidates drafts/retries and permits exactly one fixed confirmation for the trigger: “Encaminhei sua conversa para atendimento humano.” This control reply is permitted while pending; no model replies/retries are. Takeover may not suppress it. While pending/active, new minimized turns route to operator without a job, model call or repeated confirmation. Authorized release returns to automation without backlog replay. Operator replies pass ordinary disclosure checks and service-window rules. Persist transitions across restart.

Terminal model JSON is exactly `{outcome: "answer"|"clarification"|"handoff", text: string, reason: null|"customer_request"|"verification_failed"|"unsupported"|"other"}`; reason is required only for handoff. Invalid output uses fixed fallback, never raw JSON. A handoff discards model text; an explicit customer request may hand off without a model call.

The local mock visibly labels simulated statuses and enforces the 24-hour free-form window. History survives expiry; a new customer message permits resumption after revalidation. Live onboarding/delivery remains unverified. Reference: [Meta webhook behavior](https://whatsapp.github.io/WhatsApp-Nodejs-SDK/api-reference/webhooks/start/) (archived SDK, not a dependency).

## Worker and dispatch

Deadline is `received_at + TURN_DEADLINE_SECONDS` (default 60s; raise only for slow local models), measured from complete body receipt through send acceptance, including validation/queueing; status callbacks are outside it. Persist UTC deadline/counters; use monotonic elapsed time in-process. Stop model/tool work 5s before the deadline. Per turn: 3 model requests, 4 tools; model attempt ≤60s wall (Ollama: `OLLAMA_TIMEOUT_SECONDS`, default 180s, capped at 300s), tool ≤2s, Meta send ≤5s, each clipped to remaining deadline. One shared retry maximum, only for a proven safe transient failure. A final answer, clarification, handoff or exhausted budget is terminal.

Validate disclosure, references, size, takeover, authorization and source versions before queueing and again before dispatch. Stale/unsafe/timeout drafts are discarded; use the fixed fallback without another model turn, or durable operator-visible notification if delivery is blocked. Worker checks pending deadlines every 250ms, including during provider waits. If second 60 prevents sending, persist `notification_pending`; recovery may send only within service window and while automation remains enabled. Takeover leaves notification to operator; after expiry, wait for a customer message and prepend it. Unknown sends are never repeated; every outcome remains operator-visible.

Send text to `/{version}/{phone-number-id}/messages` with authorization and `{messaging_product:"whatsapp",to,type:"text",text:{body},context?:{message_id}}`. Acceptance returns provider `messages[].id`; signed callbacks separately update state. Transport success is not delivery. Free-form customer/operator sends require 24h from the latest authenticated customer `messages[].timestamp`, not receipt time. Reject >60s future skew; clamp smaller skew to receipt. Persist UTC; convert service-hours notices to `America/Campo_Grande`. Approved templates are out of scope. Reference: [Meta text endpoint](https://www.postman.com/meta/whatsapp-business-platform/request/8gvd47s/send-text-message).

## Durable job and send recovery

- In a short transaction claim only the oldest pending conversation job via conditional `pending → running` plus worker-generation token; one running job/conversation. Singleton lease renews each second, expires after five; acquire before claim/send. Persist counters before provider calls; stale generations cannot finalize/send. Cap DB lock waits at one second.
- On restart, pending jobs retain original deadlines. Expired-generation running jobs become `interrupted`, get fixed failure outcome and never rerun. Takeover routes pending messages; release does not replay. Queued replies resume only after current authorization/source/window/deadline checks.
- Persist reply before I/O; set `queued → sending` immediately before HTTP. Crash, post-transmission timeout, missing/invalid acceptance ID or lost response means `unknown`, never auto-resend. Commit acceptance ID before exposing success. Retry only pre-transmission failures or explicit transient rejection under shared retry/deadline.
- If signed status arrives before acceptance commit, persist minimized unmatched status by business-phone/provider ID/recipient, acknowledge, then reconcile on acceptance and restart. Never match by recipient alone. Without trustworthy mapping, retain unknown and expose unmatched status. Cap unmatched statuses at 1,000/24h; overflow returns 503 without acknowledging unpersisted work.
- Deduplicate status by scope/provider ID/status/time. Advance `sent → delivered → read`; failure cannot erase delivered/read, though later delivery/read may supersede failure with safe audit marker. Status never invokes model; reduce error payloads to bounded categories.

## Supported text-message workflow

For “O Takamine GD20 está disponível e posso devolver se me arrepender?”: CLI signs a representative webhook; shared ingress verifies/minimizes/deduplicates and durably accepts; worker may load up to five prior accepted turns (10 messages/12 KiB) from the same conversation, sender and source snapshot after re-minimizing and excluding stale/unauthorized/pending/failed/future work; model calls catalog and policy tools; application validates draft then rechecks before Meta-client send; mock returns provider ID and later signed status. Current catalog/policy facts are queried again. If catalog fails but policy succeeds, answer the supported policy and say availability is unconfirmed. Model failure uses fixed fallback.

## Staff source maintenance

Detailed CSV/PDF publication semantics are in [ADR-0003](adr/0003-protected-source-maintenance.md) and [ADR-0002](adr/0002-pdf-ingestion-and-retrieval.md); validation evidence and threat boundaries: [validation](validation.md), [security review](security-review.md).

- `/equipe/fontes/` requires active Django staff and source-specific view/edit grants. Publish requires per-source grant or `publish_sources`; delete needs separate delete grant and preview-bound confirmation; rollback requires `rollback_sources` plus access to affected sources. Configure accounts/groups via Django auth APIs; no bootstrap command. Session/CSRF protect POST writes.
- Six fixed CSVs and policy PDF have searchable/paginated active snapshots. Edits/uploads stage in user-owned drafts; CSV modes: append/upsert/replace. Preview diffs, validate complete bundle, then publish that reviewed revision. Broken references block; removed rows are deletions, never merged back/cascaded. Conversation/job state survives source changes.
- Bundle contains all CSVs, PDF, extraction/review versions, public passage manifest, enforced PIX metadata and hashes. PDF approval pins candidate hash/revision; replacement invalidates review. Maintainer reviews pages, passages/locators/audience/conflicts and PIX rule, attesting other rules/contacts/schedules unchanged. Only supported full-PIX discount is executable; unsupported semantics block publication.
- Limits: CSV 2 MiB; PDF 10 MiB/20 pages/128 KiB extracted text; bundle 32 MiB/10,000 rows per source; PDF parsing runs in-process with no separate timeout; staging 30s. pypdfium2 extraction; empty pages/extraction errors block. Over-limit or timeout keeps active version.
- Public policy lookup validates locators, returns ≤3 reviewed passages of ≤400 code points, lexical/Portuguese intent ranking, provenance; no match differs from source failure. Rebuild prices before active pointer switch. Activation checks expected base version and records audit in a SQLite transaction; never overwrite active files. Rollback reactivates hash-checked retained bundle/review/prices and audits it.
- Duplicate/structurally invalid sources fail staging. CSV publication does not rewrite historical order prices. Schedule/holiday/contact/delivery rule changes need code and regression support. Dispatch rechecks active source; full cached-history/multi-turn acceptance remains separate.
